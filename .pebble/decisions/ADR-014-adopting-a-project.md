## ADR-014: Adopting a project already under way: base camp and short paths
Status: accepted (2026-11-24)
Context: Pebble assumes it starts from a `bootstrap.md` and an empty folder. Most real projects already have code, conventions and tests. Their work isn't a linear roadmap but features, bugs and fixes. A roadmap written as if the project started today would ignore the existing code, or rebuild it as fake steps.
Decision:
- **"Adopt the project"**: when a folder has code but no `.pebble/`, the start command offers to adopt it instead of writing a bootstrap. Pebble reads the file tree, the manifest (`package.json` or equivalent), configuration files, the README, the existing tests and a summary of the git history (MODE: ADOPT).
- **It proposes what exists, not what should exist**: a bootstrap describing the project and its stack; ADRs for the choices already made in the code, marked `Status: detected from the code` until the developer confirms or corrects them; the architecture as it is. If the code contradicts itself (two styles for the same thing), it is flagged as a decision to take, with a single question. Confirmed ADRs then weigh like any other: Pebble never proposes a different tool than the one in use.
- **Base camp**: the existing code becomes step 0, already closed. It is a snapshot (modules, tests, how many green), not invented tasks. At adoption Pebble runs the tests once: tests already red are recorded as "red on arrival", so they don't look like the developer's work or progress.
- **Short paths for features and bugs**: after the base camp the roadmap is a list of paths, each 2 to 6 tasks, prepared just in time like the steps (ADR-011). A feature path: tests, structure, implementation, review. A bug path always starts with "write the test that reproduces the bug", which must go red first (ADR-010). The developer opens a path from a command ("New feature", "New bug") with one sentence; Pebble prepares the tasks from the code as it is now.
- **New projects join the same model**: when the initial roadmap is finished, mini-calc too lives on feature and bug paths.
- **The map** (ADR-013) shows the base camp and the paths branching from it, each with its diary. The diary starts on the day of adoption; git history appears only in the base camp's snapshot.
Alternatives ruled out: asking the developer to write a bootstrap for an existing project (slow, and it would describe the project as they remember it, not as it is); rebuilding the past as closed steps (invented history); one long roadmap for an existing project (it doesn't match how work arrives: one feature or bug at a time).
Consequences: a new mode, ADOPT, with its evals on at least one real project not written for Pebble. The path format gains a kind per section (step, feature, bug) and the base camp section. Detected ADRs need a clear status so the developer knows what to check. Reading a large repository must stay within a context budget: the tree, the manifest, configuration and a sample of files, not everything.

Update 2026-11-26: before proposing adoption, Pebble classifies the open folder by its first two levels (`core/folder.ts`). A manifest of any common stack, or code, at the root means an existing project to adopt. Manifests only in subfolders mean a folder of projects (like `~/dev`): Pebble offers to create a new folder for the new project, named from the bootstrap and opened in place of the current one, or to open one of the projects found. The tasks never create the project's folder (prompt v1.9): the open folder is always the project's root.
